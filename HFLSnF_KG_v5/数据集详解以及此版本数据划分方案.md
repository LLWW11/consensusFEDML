## 一、FB15k-237 数据格式与三元组结构

### 1.1 物理文件形态（KG-Dataset.md 没讲到的部分）

标准 FB15k-237 发布包在 `data/FB15k-237/` 下**只有三个纯文本文件**，我实测确认：

| 文件        | 行数        | 说明       |
| ----------- | ----------- | ---------- |
| `train.txt` | 272,115     | 训练三元组 |
| `valid.txt` | 17,535      | 验证三元组 |
| `test.txt`  | 20,466      | 测试三元组 |
| 合计        | **310,116** |            |

**关键点**：官方包**不带** `entity2id.txt` / `relation2id.txt` 映射文件（KG-Dataset.md 第四节说"通常还需要额外的 entity2id、relation2id 映射文件"，但这在 V5 里不存在）。V5 是**运行时按首次出现顺序自动建立编号**的。

每行是一个三元组，**制表符（`\t`）分隔三列**。实际文件样例：

```text
/m/027rn    /location/country/form_of_government    /m/06cx9
/m/017dcd   /tv/tv_program/regular_cast./tv/regular_tv_appearance/actor   /m/06v8s0
/m/05hs4r   /music/genre/artists    /m/01pbxb
```

- **第 1 列**：头实体，Freebase MID（Machine ID），形如 `/m/xxxxx`，是实体"身份证号"。
- **第 2 列**：关系谓词，Freebase 类型层级路径，如 `/film/actor/film./film/performance/film`。**注意路径中带点号且可能极长**——这是 Freebase 展开 CVT（复合值类型/中介节点）后留下的属性链。
- **第 3 列**：尾实体，同样是 MID。

### 1.2 代码里如何表示三元组

V5 的 `tasks/kge/data.py` 定义了两种表示：

```python
TextTriple = Tuple[str, str, str]   # 文本形式 (head_MID, relation_path, tail_MID)
IdTriple   = Tuple[int, int, int]   # 编码后 (head_id, relation_id, tail_id)
```

核心数据结构是 `KnowledgeGraphDataset`（data.py:17），包含：
- `train_triples / valid_triples / test_triples`：形状 `[N, 3]` 的 `torch.long` 张量，每行 `(head_id, relation_id, tail_id)`
- `entity_to_id: Dict[str, int]`、`relation_to_id: Dict[str, int]`：字符串→编号映射
- `all_true_triples: Set[IdTriple]`：训练+验证+测试的并集，用于**过滤式评估（filtered）**时剔除其它真三元组

**自动编号逻辑**（`build_knowledge_graph_dataset`，data.py:152）：
1. 先编码 **train**，`_assign_id` 按字符串首次出现顺序分配 `0,1,2,...`；
2. 再编码 **valid**、**test**，二者中出现的新实体/关系追加编号；
3. 因此编号顺序由训练集决定，验证/测试里的新实体补在尾端。

**三大完整性校验**：
- 文件内不允许重复三元组（`_read_text_triples` 用 `seen` 集合检测，遇到重复直接 `ValueError`）；
- 校验每个拆分张量形状是 `[N,3]`、编号非负且不越界（`__post_init__`）；
- **跨划分重叠检查**：train∩valid、train∩test、valid∩test 任一非空即报错（data.py:177-182）。

> 注意：FB15k-237 相比原版 FB15k，本身已通过"每对逆关系只保留一个方向"去除了测试泄漏，所以这里只做重复性与重叠性检查，不需要再处理逆关系。

## 二、V5 的数据划分

V5 的数据划分入口是 `experiment.py` 的 `build_federated_data(args, dataset)`（experiment.py:65），按 `partition_strategy` 字段分发。V5 支持 4 种策略，常量定义在 `federated_data.py:16-33`：

| 策略常量                               | 字符串                                 | 状态                         |
| -------------------------------------- | -------------------------------------- | ---------------------------- |
| `BALANCED_HEAD_ENTITY`                 | `balanced_head_entity`                 | v3/v4 基线，V5 保留          |
| `BALANCED_HEAD_ENTITY_OVERLAP_TARGET`  | `balanced_head_entity_overlap_target`  | v4 引入，V5 保留             |
| `SEMANTIC_DOMAIN_GRAPH_LOCAL_BALANCED` | `semantic_domain_graph_local_balanced` | **V5 新增，正式主力策略**    |
| `RELATION_STRATIFIED_TRIPLE_BALANCED`  | `relation_stratified_triple_balanced`  | 关系分层，仅定义未在入口分发 |

V5 的正式配置（`configs/graph_semantic/graph_semantic_hflsnf_seed42_150round_cuda.yaml` 等）使用的是 **`semantic_domain_graph_local_balanced`**，37 个客户端、负载容差 `0.05`、搜索重启 8 次、要求 `partition_search_seed == random_seed`。下面重点讲它，同时说明它相对基线策略的差异。

### 2.1 语义域提取（`graph_semantic_partition.py`）

`freebase_relation_domain(relation_name)`（line 45）：把 Freebase 关系路径按 `/` 拆段，取**第一个有效段**作为顶级语义域；`/user/...` 统一归入 `user`。

例如：
- `/film/actor/film./film/performance/film` → `film`
- `/location/location/contains` → `location`
- `/people/person/profession` → `people`

V5 训练集 237 种关系被归并为 **30 个语义域**（F11/film、location、people、award、music、organization、sports、tv、user…）。

### 2.2 不可拆分包（`_SemanticPacket`，line 30）

按 **(语义域, 头实体)** 即 `(domain, head_id)` 把训练三元组打包成原子单元（`_build_semantic_packets`，line 73）。一个包的属性：
- `domain`：该包所属语义域
- `head_id`：头实体
- `row_indices`：该包包含的训练集行号
- `entity_ids`：包内所有头尾实体并集（用于图局部性计算）
- `triple_count` = `len(row_indices)`

V5 训练集共产生 **33,155 个"域-头实体"包**（在 `client_partition_summary.json` 的 `domain_head_packet_count` 中可见）。

**关键语义**：同一头实体若出现在不同语义域的多个三元组里，会被拆成多个包、可能分发到多个客户端（打破了 v3/v4 的"头实体互斥"），但**同一域内的同一头实体绝不拆开**——这是保证头实体嵌入在语义一致上下文里训练的前提。

### 2.3 主域配额：最大余数法（`_largest_remainder_quotas`，line 98）

按每个语义域的三元组占比，把 **37 个客户端名额**分配给各域：
1. 对每个域算精确值 `client_count * count / total`，向下取整；
2. 按小数部分从大到小（同小数再按域规模、域名）把剩余名额逐个 +1；
3. 保证配额总和恰为 37。

例如 film 域三元组多，就可能分到多个客户端名额。每个客户端随后被指定一个"主域"。

`_primary_domain_sequence`（line 129）：把配额展开成 37 个域名，再用固定种子 `restart_seed` 打乱，得到每个客户端的主域序列。

### 2.4 多重启贪心分配（`_assign_packets_once`，line 184）

这是划分的核心算法。过程：

1. 计算全局均值负载 `mean_load` 和**硬上界** `upper_limit = ⌊mean_load * (1+load_tolerance)⌋`；
2. 用固定种子生成客户端打平排序 `tie_ranks`；
3. 对所有包按"**包大小降序 → 固定种子打平 → 域名 → 头实体**"排序（`_packet_order`），逐个放置；
4. 对每个包，先找能从当前负载**塞进上界**的"可行客户端"集合（不超上界）；若没有则退化为全部客户端；
5. 用三级评分键选包放置（`_assignment_score`，line 166）：
   - **①** 语义一致性：`0` 若客户端主域 == 包所属域，否则 `1`（主域匹配优先）；
   - **②** 图增量：`len(packet.entity_ids - client_entities)`，即包内有多少实体是客户端**还没**有的（越小越优先 → 实体局部复发、图连通性强）；
   - **③** 当前负载（越低越优先）；
   - **④** 稳定的打平次序。

### 2.5 低负载修复（`_repair_underloaded_clients`，line 259）

贪心分配后，个别客户端可能低于下界 `lower_limit = ⌈mean_load * (1-load_tolerance)⌉`。修复阶段：
- 按负载升序处理"欠载"客户端；
- 从其它高负载客户端收集候选包，按"**移动后语义纯度损失最小 → 图增量最小 → 打平次序**"排序（`_move_penalty`）；
- 逐个移动，守上下界：源端移出后不低于下界、目标端移入后不高于上界。

这样最终保证每个客户端负载都在 `[lower_limit, upper_limit]` 内。

### 2.6 多重启搜索与候选选择（`partition_train_triples_by_semantic_domain_graph_local`，line 613）

V5 默认 `search_restarts=8`，即用 `seed + restart_index * 104729` 做 8 次不同随机种子重启。每次重启走完整的"主域分配 → 贪心放置 → 低负载修复"，并快速计算一个候选评分元组（`_raw_assignment_score`，line 564）：

```
(violations, max_relative_load_deviation, 1 - 主域三元组占比,
 entity_occurrences / num_entities, digest_hash)
```

其中：
- `violations`：负载偏差超过容差 + 是否有空客户端；
- 主域三元组占比越高越好（语义聚焦）；
- 实体复制因子（出现客户端数）越低越好（图局部）。

然后取 8 次中**字典序最小**的候选构造正式分区（`_partition_candidate`）。若最优候选仍有 `violations > 0`，直接抛 `RuntimeError` 拒绝（line 663）。最终返回的 `FederatedKnowledgeGraphData` 带一个 `SHA-256 划分指纹`（`_partition_hash`，federated_data.py:568，按客户端编号+该客户端有序三元组字节计算）。

### 2.7 一致性/门禁/合同

- 每次运行还会把 `partition_hash` 与 YAML 中的 `expected_partition_hash` 比对，不一致直接拒绝（防错误划分混入消融实验）。
- `semantic_graph_statistics`（line 398）为每个客户端输出语义纯度、归一化域熵、关系分布 JS 散度、实体局部复发率、最大连通分量占比等质量指标，供合同门禁检查。
- V5 的正式 `graph_semantic_hflsnf_seed42_150round_cuda.yaml` 用于 150 轮训练；种子 42/2024/2025 的正式分区哈希分别为 `fe461e19...`、`f1e9e430...`、`30fda49e...`，三者互异且已独立复算一致。

### 2.8 与 v3/v4 基线策略的对比（为什么 v5 更强）

| 维度                   | v3/v4 `balanced_head_entity` | **v5 `semantic_domain_graph_local_balanced`**     |
| ---------------------- | ---------------------------- | ------------------------------------------------- |
| 原子单元               | 头实体（整头互斥）           | (语义域, 头实体) 包                               |
| 头实体归属             | 严格互斥（1.0）              | 可跨域多客户端（均值 2.27）                       |
| 关系种数/客户端        | ~32（接近全集 237，"全才"）  | **4.68（"关系专家"）**                            |
| 语义纯度               | 无语义概念，全域混杂         | **91.98%**                                        |
| 三元组负载             | 极均衡（std<1，7354-7355）   | 5% 容差内（6987-7722，max偏差0.04997）            |
| 实体出现客户端数均值   | 9.75（高度散落）             | 5.59（更局部）                                    |
| 官方测试 MRR（3-seed） | 0.3433                       | **0.3900（+13.6%）**，head MRR 提升最大（+20.9%） |

这也是 v5 相对 v3/v4 的唯一变量——训练/聚合 12 个核心文件 MD5 完全一致（见 `v5_vs_v3v4_提升原因分析.md`）。

> 需要说明的运行规律：三元组 **唯一完整覆盖** 在所有策略下都成立（无重复、无遗漏）；FB15k-237 **没有真实机构所有权标签**，语义域只是"现实代理"划分，文档中明确不得称为真实机构划分。

## 三、总结一句话

**FB15k-237 = 三个制表符分隔的三元组文本（train 272115 / valid 17535 / test 20466），每一行 `头实体MID \t 关系路径 \t 尾实体MID`，代码按首次出现顺序自动编号成 `[N,3]` 长整型张量并做重复/重叠校验。** V5 的数据划分核心是 `semantic_domain_graph_local_balanced`：把 237 种关系映射成 30 个 Freebase 顶级语义域，按 (域,头实体) 打成 33,155 个不可拆分包，用最大余数法给 37 个客户端分主域名额，再经 8 次种子化重启的"主域优先→图增量小优先→负载低优先"贪心放置 + 低负载修复，产出负载偏差 ≤5%、语义纯度约 92% 的分区，并以 SHA-256 划分哈希 + 合同门禁保证可复现。





## 四、真实配额结果（seed42，37 个客户端）

| 语义域                                                       | 训练三元组占比 | 分到几个客户端 | 说明                       |
| ------------------------------------------------------------ | -------------- | -------------- | -------------------------- |
| award                                                        | 26.75%         | **10**         | 最大域，分到最多           |
| film                                                         | 20.93%         | **8**          |                            |
| people                                                       | 13.02%         | **5**          |                            |
| music                                                        | 8.31%          | **3**          |                            |
| location / education                                         | 5.17% / 4.63%  | 各 **2**       |                            |
| sports / base / olympics / soccer / tv / organization / common | 1.3%~3.4%      | 各 **1**       |                            |
| 其余 17 个小域（government、media_common、user、food、travel…dataworld，合计约 6%） | <1.2%          | **0**          | 没有任何客户端以它们为主域 |
| **合计**                                                     | 100%           | **37** ✓       |                            |

**不是每种关系只分到 1~2 个客户端**，而是：

- **一个域可以对应多个客户端**：award 对应 **10 个**、film 对应 **8 个**、people 对应 **5 个**——大域拥有更多"专家客户端"；
- 中等域分到 1~2 个；
- **17 个小域一个客户端都分不到**（它们的三元组会被"塞进"别的客户端）。

这个配额直接体现域的大小：award 拿到 10/37≈27%，正好匹配它 26.75% 的三元组占比。

## 五、主域 ≠ 客户端里只有这个域

主域只是**偏好标签**，不代表客户端"独占"这个域。真实分区里（seed42）：

| 客户端                                                   | 主域     | 实际含几个域 | 主域三元组占比               |
| -------------------------------------------------------- | -------- | ------------ | ---------------------------- |
| client 1, 3, 4, 6, 8, 12, 13, 20, 28, 29, 34（共 11 个） | 各不相同 | **1**        | 100%（纯单域）               |
| client 0, 2, 9, 10, 21, 22, 25, 30~33, 36（共 11 个）    | —        | **2**        | 71%~99%                      |
| client 5, 15, 26, 35                                     | —        | 9~13         | 94%~97%                      |
| client 18                                                | common   | **21**       | **仅 51.7%**（一半是别的域） |
| client 19                                                | soccer   | 19           | 72.5%                        |

37 个客户端实际含域的数量分布：1 个域 × 11 个、2 个域 × 11 个、3~5 个 × 4 个、9+ 个 × 4 个，**最杂的客户端横跨 21 个域**。

为什么会这样？因为贪心分配时"主域匹配优先"，但遇到**装不满负载**时（尤其是小域的三元组包），会把非主域的包也放进来；最后的"低负载修复"阶段更是会从高负载客户端**批量搬包**，进一步引入非主域内容。所以最终效果是：**每个客户端约 92% 的三元组属于其主域**（三元组加权纯度 0.9198），其余约 8% 是"杂质"。


> V5 的划分逻辑是"**每个客户端一个主域，主域名额按域大小成比例分配**"：award/film/people 等大域各拥有 5~10 个客户端，小域只有 1 个甚至 0 个；而主域只是偏好标签，客户端实际内容是"主域为主（~92%）+ 少量其它域"的混合体。所以不能说"每种关系只能到 1~2 个客户端"——**一个域最多可到 10 个客户端，也有 17 个域一个都分不到，且几乎每个客户端都掺有非主域的三元组**。

## 六、语义—图局部性双消融的数据边界

双消融继续使用完全相同的FB15k-237训练集和33,155个“语义域＋头实体”包，不修改原始文本、运行时编号或包内三元组。

- 消融A删除主域配额和主域匹配目标，只保留实体图局部性、负载约束和稳定平局次序。语义域仅用于事后统计，因此报告中只能称“事后主导域”，不能称“客户端主域”。
- 消融B保留完整V5的主域配额，但删除所有实体交集和新增实体数目标。它仍以“域＋头实体”为不可拆分包，相关实体通过同域多个客户端之间的负载轮转自然分散。
- 两个实验臂都维持37个客户端、8次确定性重启和最大负载偏差不超过5%，从而避免把计算负载变化混入机制比较。

完整V5、消融A和消融B分别表示“语义＋图”“仅图”“仅语义”。本轮不增加“语义和图都没有”的第四实验臂，因此只能比较删除一个机制后的边际变化，不能计算严格的二因素交互效应。
