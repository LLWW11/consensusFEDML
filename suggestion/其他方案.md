## 核心判断

可以找到多种比 MNIST/FEMNIST 更适合的任务，但要先明确一个实验原则：

> **“客户端数量增加”本身不保证效果提高；只有当新增客户端带来新增知识、新增视角、新增类别或新增空间覆盖时，性能才有较稳定的上升预期。**

若把固定数据集简单切成更多客户端：

[
|\mathcal D|=\text{固定},\qquad
|\mathcal D_k|\approx\frac{|\mathcal D|}{K}
]

客户端越多，每个客户端数据反而越少，Non-IID 和局部过拟合可能更严重，最终效果不一定提高。

要得到你希望的趋势，主实验应采用：

[
K\uparrow
\quad\Longrightarrow\quad
\text{有效信息覆盖量}\uparrow
]

例如新增客户端带来：

- 新的知识图谱关系；
- 新的实体及三元组；
- 新的传感器视角；
- 新的攻击类型；
- 新的道路区域；
- 新的文档知识源。

而且客户端集合最好采用嵌套设置：

[
\mathcal C_2
\subset
\mathcal C_4
\subset
\mathcal C_8
\subset
\mathcal C_{16}
]

这样才能清楚说明新增客户端具体增加了什么信息。

| 多源联邦知识图谱补全  | 新关系、新三元组、新实体知识 | 很强         | 较高          | 很高      | 中       |

| 多智能体协同感知      | 新空间视野、消除遮挡         | 很强         | 较低          | 很高      | 高       |

1. **多源联邦知识图谱补全；**
2. **联邦入侵检测中的攻击类型互补；**
3. **联邦时空交通图预测。**

多智能体协同感知和 Federated RAG 更接近真正的 IoA，但迁移成本较高。

# 二、方案一：多源联邦知识图谱补全

这是目前与你的叙事最匹配的方案。

## 1. 场景定义

每个客户端智能体拥有一个局部知识图谱：

[
G_k=(V_k,R_k,T_k)
]

其中：

- (V_k)：本地实体；
- (R_k)：本地关系类型；
- (T_k)：本地三元组。

例如：

```text
客户端1：人物—出生地、人物—国籍
客户端2：人物—职业、人物—组织
客户端3：电影—演员、电影—导演
客户端4：组织—所在地、组织—成员
```

新增客户端意味着新增知识领域：

[
\bigcup_{k=1}^{K}T_k
]

不断扩大。

FedE 的出发点就是多个相关但彼此隔离的知识图谱可以通过联邦训练互相补充知识，而不需要直接交换原始三元组。([arXiv](https://arxiv.org/abs/2010.12882?utm_source=chatgpt.com))

## 2. 为什么容易出现客户端越多越好

假设测试问题是：

[
(h,r,?)\rightarrow t
]

客户端 1 只知道 (h) 的国籍，客户端 2 知道其所在组织，客户端 3 知道组织所在地。单个客户端可能无法形成完整表示，多个客户端的共享实体和关系知识可以改善实体嵌入。

可定义知识覆盖率：

[
C_T(K)=
\frac{
\left|\bigcup_{k=1}^{K}T_k\right|
}{
|T_{\mathrm{all}}|
}
]

关系覆盖率：

[
C_R(K)=
\frac{
\left|\bigcup_{k=1}^{K}R_k\right|
}{
|R_{\mathrm{all}}|
}
]

预期关系为：

[
C_T(K)\uparrow,\ C_R(K)\uparrow
\quad\Longrightarrow\quad
\mathrm{MRR},\mathrm{Hits@K}\uparrow
]

## 3. 最适合的数据划分

不要随机平均切三元组。建议采用：

### 关系互补划分

客户端分别持有不同关系集合，但保留一定共享实体。

例如 FB15k-237 有多种关系，可以先按照关系频率或语义簇划分：

```text
Client 1：人物关系
Client 2：地理关系
Client 3：影视关系
Client 4：组织关系
```

### 图社区划分

对实体图进行社区发现，每个客户端获得一个局部社区，同时保留边界实体作为共享锚点。

### 长尾关系划分

少数客户端拥有稀有关系。客户端数量增加后，尾部关系逐渐被覆盖，因此 Macro-MRR 和稀有关系 Hits@10 会明显提高。

## 4. 与现有 HFL 的结合

```text
局部知识图客户端
        ↓
本地 TransE/DistMult 训练
        ↓
边缘服务器聚合区域实体表示
        ↓
云端聚合共享实体和模型参数
        ↓
全局知识表示下发
```

但不要直接平均不对应的实体嵌入。第一版可以使用：

- 全局统一 `entity2id`；
- 全局统一 `relation2id`；
- 所有模型参数形状相同；
- 只聚合本轮被本地三元组更新过的实体；
- 对共享实体做掩码加权聚合。

后续可以参考 PFedEG 的客户端关系图，对语义相关客户端给予更高聚合权重，避免无关客户端增加后引入噪声。([arXiv](https://arxiv.org/abs/2406.11943?utm_source=chatgpt.com))

## 5. 综合评价

这是最推荐的主方案：

- IoA 叙事自然；
- 客户端就是不同知识持有者；
- 新客户端带来明确的新知识；
- 与掉线、边缘中继、知识覆盖率结合方便；
- 可以使用你已有的分层参数聚合结构；
- MRR、Hits@K 对知识数量和关系覆盖较敏感。

------

# 三、方案二：关系增量或技能增量联邦学习

这可以看作知识图谱方案的增强版本。

## 1. 基本思想

每个客户端智能体具有一种或几种专门能力：

```text
Agent 1：识别人和组织的关系
Agent 2：识别地点和事件的关系
Agent 3：识别交通和道路状态
Agent 4：识别异常和安全威胁
```

新增客户端等价于新增技能：

# [ \mathcal S_K

\bigcup_{k=1}^{K}\mathcal S_k
]

因此系统技能覆盖率自然增加。

已有联邦类别增量学习研究专门考虑新客户端携带新类别进入联邦系统的情况，以及如何缓解全局模型遗忘旧类别的问题。([arXiv](https://arxiv.org/abs/2310.08948?utm_source=chatgpt.com))

## 2. 在你的任务中如何落地

不必使用 CIFAR-100。可以做成：

### 关系增量 KGC

每个新增客户端带来一组新的知识图谱关系：

```text
第1阶段：20种关系
第2阶段：增加20种关系
第3阶段：再增加20种关系
```

测试集始终包含全部关系。

随着客户端增加：

- 全部关系上的 Macro-MRR 提高；
- 未见关系比例下降；
- 系统可回答的查询类型增多。

定义技能覆盖率：

# [ C_{\mathrm{skill}}(K)

\frac{
|\bigcup_{k=1}^{K}R_k|
}{
|R_{\mathrm{test}}|
}
]

还可以报告：

[
\mathrm{MRR}*{\mathrm{seen}},
\qquad
\mathrm{MRR}*{\mathrm{new}},
\qquad
\mathrm{MRR}_{\mathrm{all}}
]

## 3. 这个方案的优点

它比普通“数据量增加”更适合解释客户端数量效应：

> 系统性能提高，不只是因为训练样本变多，而是因为智能体群体的能力集合变得更完整。

这与 IoA 中的：

- agent discovery；
- dynamic team formation；
- skill composition；
- specialist agents；

更加一致。

## 4. 风险

若直接使用 FedAvg，新关系对应的参数可能被不拥有该关系的客户端稀释。更适合使用：

- 关系参数掩码聚合；
- 类别原型聚合；
- 共享编码器 + 本地关系头；
- 知识蒸馏。

因此实现难度略高于普通 TransE。

------

# 四、方案三：联邦多视图语义融合

## 1. 场景定义

多个智能体观察同一对象或同一事件，但每个智能体只能看到一个视角：

```text
智能体1：图像特征
智能体2：文本描述
智能体3：音频特征
智能体4：结构化关系
```

或者：

```text
摄像头1：正面视角
摄像头2：侧面视角
摄像头3：远距离视角
```

多视图学习的核心是从不同视角中提取互补信息。近年来的联邦多视图聚类工作也明确把不同客户端的视图互补作为主要信息来源，并研究缺失视图条件下的联合学习。([Proceedings of Machine Learning Research](https://proceedings.mlr.press/v267/chen25az.html?utm_source=chatgpt.com))

## 2. 为什么客户端数量效应明显

设第 (k) 个客户端提供视图 (x^{(k)})，融合表示为：

[
z=
\operatorname{Fuse}
\left(
z^{(1)},z^{(2)},\ldots,z^{(K)}
\right)
]

新增客户端增加一个新视角：

[
K\uparrow
\quad\Longrightarrow\quad
\text{视图覆盖率}\uparrow
]

尤其当单一视图存在：

- 噪声；
- 遮挡；
- 缺失；
- 模态不完整；

时，新增客户端的增益通常会更加明显。

## 3. 轻量数据集与重型数据集

第一版可使用多视图聚类或分类数据集，例如：

- BDGP；
- Caltech101-20；
- Scene-15；
- Handwritten multi-view。

每个客户端持有一种视图。

更贴近 IoA 的版本可使用：

- 多摄像头；
- LiDAR + Camera；
- 车端 + 路侧端；
- 多源语义传感器。

## 4. 与现有框架的差别

它不再是普通水平联邦学习，因为不同客户端可能持有同一批对象的不同特征，接近垂直联邦或联邦多视图学习。

聚合对象可能从：

```text
模型参数
```

变成：

```text
共享表示、原型、图结构或伪标签
```

因此 HFL 的通信层和边缘—云结构可以保留，但本地训练和聚合模块需要较明显调整。

## 5. 综合评价

数量增益预期很强，但代码改造比联邦知识图谱更大。

------

# 五、方案四：多智能体协同感知

这是最容易得到“参与智能体越多，感知效果越好”的任务之一。

## 1. 场景

每个车辆、无人机或路侧单元只能看到局部环境：

[
O_k=\operatorname{Observe}_k(S)
]

多个智能体融合：

[
\hat S=
\operatorname{Fuse}
(O_1,\ldots,O_K)
]

新增智能体可以：

- 减少遮挡；
- 扩大视野；
- 增加点云密度；
- 提高远距离目标可见性。

TUMTraf-V2X 的实验中，车路协同多模态融合相对于仅使用车端 Camera-LiDAR 模型，3D mAP 增加了 14.36 个百分点，表明补充路侧感知具有明显效果。([开放获取计算机视觉论坛](https://openaccess.thecvf.com/content/CVPR2024/html/Zimmer_TUMTraf_V2X_Cooperative_Perception_Dataset_CVPR_2024_paper.html?utm_source=chatgpt.com))

CORE 也将多智能体联合观测解释为更完整的环境观测，并在 OPV2V 和 V2X-Sim 上研究检测和语义分割。([开放获取计算机视觉论坛](https://openaccess.thecvf.com/content/ICCV2023/html/Wang_CORE_Cooperative_Reconstruction_for_Multi-Agent_Perception_ICCV_2023_paper.html?utm_source=chatgpt.com))

## 2. 与你的通信研究很契合

该方案可以直接加入：

- 客户端掉线；
- 路侧单元失效；
- 传输时延；
- 发送特征大小；
- 中继聚合；
- 通信资源限制；
- 智能体选择。

可以研究：

## [ \max_{\mathcal S\subseteq\mathcal C} \quad \mathrm{mAP}(\mathcal S)

\lambda\operatorname{Cost}(\mathcal S)
]

这与你已有的 TS-MLG、路径可达性、调度和存储辅助框架也很容易建立联系。

## 3. 不足

主要问题是：

> 协同感知通常需要推理阶段的特征融合，而不只是训练阶段的 FedAvg。

因此它不是简单替换数据集和模型，而是需要加入第二条数据流：

```text
训练阶段：HFL 聚合模型
推理阶段：智能体上传感知特征并融合
```

效果很可能最显著，但短期实现成本最高。

------

# 六、方案五：联邦入侵检测中的攻击知识互补

这是最容易在你现有代码上实现，同时又容易得到明显客户端数量增益的方案。

## 1. 场景

不同 IoT 区域面对不同攻击：

```text
Client 1：DoS
Client 2：扫描与侦察
Client 3：恶意软件
Client 4：身份欺骗
Client 5：数据注入
```

单个智能体只能识别本地常见攻击。多个客户端参与后，全局模型获得更完整的攻击知识。

PROTEAN 使用类别原型在客户端间共享不同攻击类型的知识，使参与者能够理解本地数据中不存在的攻击技术。([arXiv](https://arxiv.org/abs/2507.05524?utm_source=chatgpt.com))

也已有工作直接采用 Mist—Edge—Fog—Cloud 的层级结构进行异构 IoT 入侵检测，与现有分层联邦框架在结构上较为接近。([arXiv](https://arxiv.org/abs/2511.00271?utm_source=chatgpt.com))

## 2. 为什么数量效应明显

攻击类别覆盖率：

# [ C_A(K)

\frac{
\left|\bigcup_{k=1}^{K}\mathcal A_k\right|
}{
|\mathcal A_{\mathrm{all}}|
}
]

随着客户端增加，新的攻击类型逐渐进入联邦模型。

推荐主要指标：

- Macro-F1；
- Balanced Accuracy；
- PR-AUC；
- 尾部攻击 Recall；
- 未见攻击检测率。

不要只使用普通 Accuracy，因为正常流量数量通常较多，可能掩盖稀有攻击上的改善。

## 3. 与现有框架兼容性

非常高。

仍然可以使用：

- MLP；
- 一维 CNN；
- Transformer encoder；
- FedAvg；
- 边缘聚合；
- 云端聚合。

主要只需要替换数据集和数据划分逻辑。

## 4. 不足

它非常适合 IoA 的安全场景，但与“语义推理、知识协作”相比，理论叙事稍弱。

可以将其定位为：

> 多智能体安全知识共享和跨域未知威胁识别。

------

# 七、方案六：联邦时空交通图预测

## 1. 场景定义

每个客户端对应一个道路传感器、一组道路或一个交通区域：

[
x_k(t)=
\text{客户端 }k\text{ 在时刻 }t\text{ 的交通状态}
]

任务是预测未来流量、速度或拥堵状态：

# [ \hat X(t+\tau)

f\left(
X(t-T+1:t),G
\right)
]

客户端数量增加意味着更多道路区域被观测。

已有交通预测研究使用区域和全局两层结构建模传感器依赖，也有图感知联邦聚合方法在 METR-LA 和 PEMS-BAY 上研究客户端之间的空间关系。([arXiv](https://arxiv.org/abs/2309.11284?utm_source=chatgpt.com))

## 2. 与现有 HFL 的映射

```text
道路传感器/车辆
       ↓
区域边缘服务器
       ↓
城市级云端服务器
```

模型可以选择：

- GRU/LSTM；
- STGCN；
- DCRNN；
- 简单 GCN + GRU。

边缘服务器聚合区域相邻传感器，云端聚合各区域模型。

## 3. 如何确保客户端越多越好

不能随机添加遥远且无关的传感器。应当按照目标区域相关性依次增加：

[
\mathcal C_2
\subset
\mathcal C_4
\subset
\mathcal C_8
]

优先加入：

- 空间距离近的传感器；
- 历史流量相关性高的传感器；
- 与目标道路存在上游—下游关系的传感器。

此时新增客户端带来更多有效时空上下文，MAE 和 RMSE 有较强改善预期。

## 4. 优点

- 云边端结构自然；
- 客户端数量和空间覆盖量直接相关；
- 掉线可以解释成传感器故障；
- 你的 TS-MLG 和网络路径模型可以自然进入通信部分；
- 数据规模和传感器数量都容易控制。

不足是它更接近智能交通和边缘智能，而不是通用 IoA。

------

# 八、方案七：联邦检索与分布式 RAG

这是最接近 LLM 智能体互联网的方案。

## 1. 场景

每个客户端智能体拥有一个本地知识库：

```text
Agent 1：通信知识库
Agent 2：网络调度知识库
Agent 3：设备手册知识库
Agent 4：历史故障知识库
```

用户问题到达后，各智能体分别检索本地证据，边缘节点进行区域候选聚合，云端完成全局证据重排和答案生成：

```text
Query
  ↓
多个客户端本地检索
  ↓
边缘候选证据聚合
  ↓
云端全局重排
  ↓
答案生成
```

Federated RAG 已被作为结合联邦学习与分布式外部知识的研究方向，主要问题包括隐私检索、跨客户端异构性和多知识源评估。([ACL Anthology](https://aclanthology.org/2025.findings-emnlp.388/?utm_source=chatgpt.com))

联邦检索也可以将查询路由到多个外部知识源，以处理分散在不同客户端上的知识。([ACL Anthology](https://aclanthology.org/2026.acl-long.1135/?utm_source=chatgpt.com))

## 2. 为什么客户端数量效应强

如果每个客户端拥有不同文档，新增客户端扩大候选知识库：

[
\mathcal K_K=
\bigcup_{k=1}^{K}\mathcal K_k
]

因此：

[
\operatorname{Recall@K}
\uparrow
]

尤其当一个问题的证据分散在多个知识源中时，更多客户端可能显著改善：

- Evidence Recall；
- Exact Match；
- Answer F1；
- 多跳问答准确率。

## 3. 如何接入现有 HFL

训练阶段可以保留 HFL：

```text
客户端训练本地检索编码器
        ↓
边缘聚合
        ↓
云端聚合共享检索器
```

推理阶段增加：

```text
本地检索
→ 边缘证据聚合
→ 云端重排
```

## 4. 不足

需要额外引入：

- 文本编码模型；
- 向量数据库；
- 检索指标；
- LLM 或小型生成模型；
- 多跳问答数据集。

它最贴近真正的 LLM 智能体协作，但不适合作为最短期改造方案。

# 九、怎样设计实验，才能让“客户端越多越好”可信

## 1. 主实验：增长总信息量

保持每个客户端数据量大致不变：

[
|\mathcal D_k|\approx n_0
]

增加客户端时，总信息量增加：

[
|\mathcal D_{\mathrm{total}}|
\approx K n_0
]

测试：

```text
2、4、8、12、16 个客户端
```

这回答的是：

> IoA 系统吸纳更多知识源或感知智能体时，整体能力如何扩展？

------

## 2. 必须增加一个固定总数据量对照组

保持：

[
|\mathcal D_{\mathrm{total}}|=\text{固定}
]

只把相同数据切成不同数量客户端。

这组实验很可能不会呈现明显上升，甚至下降，但它能够证明：

> 性能提升不是客户端编号本身造成，而是新增客户端带来的互补知识和覆盖范围造成。

这是审稿时非常重要的区分。

------

## 3. 控制信息互补率

定义客户端新增信息比例：

[
q_k=
\frac{
|\mathcal D_k-
\bigcup_{j<k}\mathcal D_j|
}{
|\mathcal D_k|
}
]

设置：

```text
高冗余：q = 0.1
中互补：q = 0.5
高互补：q = 0.9
```

预期：

[
q\uparrow
\quad\Longrightarrow\quad
\text{新增客户端边际收益}\uparrow
]

这样可以得到很有解释力的实验：

> 智能体数量不是唯一因素，智能体之间的知识互补程度决定了群体规模收益。

------

## 4. 增加掉线鲁棒性实验

在相同掉线率 (p) 下比较不同总客户端数：

[
K\in{4,8,16,32}
]

例如在线数量：

[
M\sim\operatorname{Binomial}(K,1-p)
]

客户端越多，系统可能拥有更多冗余知识源，部分客户端掉线后仍然可以维持知识覆盖。

可定义鲁棒性损失：

# [ \Delta Q(K,p)

Q(K,0)-Q(K,p)
]

如果：

[
\Delta Q(K_2,p)
<
\Delta Q(K_1,p),
\qquad K_2>K_1
]

就说明更大规模的智能体群体具有更高的知识冗余和掉线鲁棒性。

这与你已有的可靠性研究非常匹配。

------

# 十、最终建议

## 最平衡的主方案

[
\boxed{
\text{FB15k-237 多源联邦知识图谱补全}
}
]

建议设置为：

- 客户端按关系领域或知识社区划分；
- 每个新增客户端带来新的关系和三元组；
- 使用 TransE 或 DistMult；
- 使用共享实体掩码聚合；
- 边缘聚合区域知识；
- 云端形成全局知识表示；
- 评价 MRR、Hits@1/3/10 和关系覆盖率；
- 加入客户端掉线和边缘节点失效。

这个方案最容易同时满足：

- IoA；
- 分层联邦；
- 知识协作；
- 客户端数量效应；
- 数据量敏感性；
- 掉线可靠性。

## 最容易快速出明显结果的备选

[
\boxed{
\text{IoT 联邦入侵检测 + 攻击类型互补划分}
}
]

它对现有框架改动最少，Macro-F1 和稀有攻击召回率对参与客户端和攻击类型覆盖较敏感。

## 与你已有网络拓扑研究最容易结合的备选

[
\boxed{
\text{联邦时空交通图预测}
}
]

它能将客户端、边缘节点、地理邻接、TS-MLG 可达路径、掉线和区域聚合统一到同一个物理场景中。

不建议为了获得漂亮曲线，直接将相同数据重复分配给更多客户端。更可靠的论文结论应当是：

> 随着参与智能体数量增加，系统获得更高的知识、技能、视角或空间覆盖率，从而提高全局任务性能；这种增益取决于新增智能体提供的信息互补度，并在客户端掉线条件下体现为更强的群体冗余与鲁棒性。
